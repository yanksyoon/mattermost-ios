## 2. F1 (re-measured) — the DM case's last assertion is out of the harness's reach

The test ends by finding the new conversation in the sidebar
(`T47CreateChannelUITests.swift:371-374`) through `revealSidebarRow`, which scrolls up to 25 times,
then down up to 25 times (`:474-500`). At the moment of the red the app's own accessibility
description reports the sidebar's scroll bar as **`Vertical scroll bar, 29 pages, value: 0%`**.

The fixture is the reason, measured read-only at 18:36 HKT through the same REST API the test uses
(`GET /users/{id}/teams/{team_id}/channels`, `GET /…/channels/categories`):

* team `Perf` (`ocz148uck3r88dcjikj497bosh`) has **427 channels** for `perfprobe`: 368 public,
  56 direct, 2 group, 1 private (it was 410 on 2026-11-05).
* the sidebar categories are all uncollapsed: eight `T8G group N` custom groups (10 channels
  each), then `Channels` (319 channels), then `Direct Messages` (58). The DM category therefore
  starts roughly 399 rows below the top, and 25 fast swipes do not cross 29 pages.

The conversation the test opened is in the server's channel list, the pane opened titled with the
person, and the server-record/membership assertions before the red one passed. So the red is "the
reveal loop cannot cross 29 pages", not "the app failed to list the conversation".

This is a harness defect with a known local repair, not an inherent limit. Card `t_60bbf19d` rewrote
this same helper — read the server-drawn category order, collapse each group above Direct messages
through its header, press the DM group's `Load more`, then a bounded 10-swipe sweep — in commit
**`a8c4025`** on branch `qa/t_60bbf19d`, and its handoff reports the case green 3/3 there
(`collapsed=9 taps=9 loadMore=2 swipes=10 found=true`). `a8c4025` is **not** an ancestor of
`8a276da` (`git branch --contains a8c4025` lists only `qa/t_60bbf19d`), so the red at this HEAD is
expected and the fix is one merge away. I did not cherry-pick it here: this card re-takes the
verdict on the tree as it stands, and merging another card's unpublished branch is not a parity
re-take. The card's `suggested_follow_up` — "both findings are now green, a re-take could record
plain PASS" — is true only of that branch, not of this tree; the verdict stays PASS-WITH-FINDINGS
until the repair lands here.
