## What this does and does not measure

- **Measured:** the app process and every WebKit helper process the shell's WKWebView
  spawns, for a real Mattermost web app (server 9.11) rendering a seeded workspace;
  the scripted sequence is launch → workspace render → log in → open a channel →
  scroll N steps → open a thread, followed by an idle steady state.
- **Not a device measurement.** These are Mac Catalyst and iOS Simulator runs on this
  Mac. A device run needs: a physical iPhone/iPad on iOS 17+, `xcrun devicectl device
  process launch` with the same launch arguments, `footprint`/`vmmap` over the device
  process (via `devicectl` or Instruments' VM Tracker), and the same seeded server
  reachable over the LAN. Pages/WebContent are Jetsam-limited on device (a few hundred
  MB per process), so absolute numbers may differ; the *ratio* web-vs-native is the
  transferable result.
- **`native` mode is not a native chat screen.** It is T26's native stand-in, and (as
  T26-AV found) the shell still loads the webview behind it, so the WebContent process
  stays alive — see the headline table's `WebContent still alive in the native arm`
  column, which is what the webview release policy (`docs/dual-render.md` §12.6) has to
  drive to zero. In this arm the webview is **not mounted** (the stand-in owns the
  pane), so its virtualised post list has no height: the arm reaches an authenticated
  workspace and stops, and its footprint is a lower bound for "native card plus a live
  webview", not an equal-state comparison with `web`. The `shell` row (no server at
  all) is the honest floor a native implementation starts from.
- **First-run web-app detour:** on a fresh web-view data store the web app shows its
  linking landing page once; the probe clicks "View in Browser" the way a user does, so
  that extra SPA bootstrap is inside the measured launch.

Reproduce:

```
scripts/perf_probe.sh --server-start --targets catalyst,simulator --modes web,shell,native --posts 180 --replies 24 --scroll-steps 12 --repeat 2
```
