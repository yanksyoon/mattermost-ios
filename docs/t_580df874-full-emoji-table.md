# Reactions draw `:camera_with_flash:` as text — the pill's table was a 60-name sample

Card: `t_580df874` (reported from the native channel view).
Tree: `main` @ `d4800c3` + this card's commit.

## 1. What the reader saw

In a channel's reaction bar, `👍 4` drew as a glyph while `:lol-sob: 3` and
`:camera_with_flash: 1` were literal text inside otherwise normal pills.

A pill has exactly one place that decides what a `:name:` draws (`EmojiGlyphContent`,
`PostRowView.swift`):

```swift
if let image { Image(uiImage: image) }                       // the server's custom emoji
else { Text(EmojiShortcodes.character(for: name) ?? ":\(name):") }
```

`image` comes from `EmojiCatalogue` (`GET /emoji`), which is right. `character(for:)` read
`EmojiShortcodes.table` — **a hand-written 60-name dictionary** living in
`MarkdownView.swift` (`tada`, `heart`, `thumbsup`, `smile`, `rocket`, …). `camera_with_flash` is
not one of the 60, so a *system* emoji the server resolves perfectly well fell through to the
literal text. The same table answered the markdown renderer (`MarkdownText.text(of:)`,
`MarkdownText.composed`) and the composer's `:` completion (`ComposerViewModel.emojiCandidates`),
so all three had the same blind spot.

## 2. Why the full table already existed

T37 shipped the complete upstream set for the emoji picker:
`Mattermost/Resources/emoji.json`, generated by `scripts/t37_emoji_build.py` from
`mattermost-mobile`'s Apache-2.0 `emoji.json` (the file is verified to be that licence before it is
written), loaded by `SystemEmojiCatalogue`. Measured on the checked-in resource:

```
emojis 1805
aliases 2327
dolphin              '🐬'
sparkling_heart      '💖'
face_with_raised_eyebrow '🤨'
camera_with_flash    '📸'
```

Nothing new had to be bundled. What was missing was the *wiring*: the picker read the full table,
the three rendering paths read the sample.

## 3. The repair

1. **`EmojiShortcodes` is now a view onto the one table** (`MarkdownView.swift`):
   `character(for:)` → `SystemEmojiCatalogue.shared.character(for:)`, `isBuiltIn(_:)` likewise.
   The 60-name dictionary is renamed `fallbackTable` and is documented as what it actually is: the
   degradation used *only* when `emoji.json` is missing from the bundle (it is what
   `SystemEmojiCatalogue.shared` falls back to, and a unit test pins `degradedReason` to nil so a
   missing resource fails loudly instead of quietly shrinking the table again).
2. **The pill's precedence is a value, not a view branch** (`PostRowView.swift`):
   `EmojiGlyph.resolve(image:name:)` returns `.image` / `.character` / `.literal`, in that order —
   the server's custom emoji first (unchanged), the built-in glyph second, `:name:` only when
   neither knows the name (which is also what the web client draws). The view body is a `switch`
   over that value, and the precedence is unit-tested directly.
3. **The composer offers the whole table** (`ComposerViewModel.swift`): `:` completion searches
   `SystemEmojiCatalogue.shared.search` (same ranking the picker uses: prefix, then contains, then a
   deterministic subsequence tier) instead of 60 names. Two details kept deliberate:
   * before the reader types anything the list stays the starter set (`EmojiShortcodes.starterNames`,
     names only — their glyphs come from the table), not all 1,805 rows;
   * the row is labelled with the alias the reader typed toward — `:thumb` answers `thumbsup`, not
     the canonical `+1` (both are the same emoji server-side; `getEmojiFirstAlias` still governs
     what a *reaction write* sends, which T37's tests pin separately).

## 4. Tests

`MattermostTests/EmojiShortcodeTableTests.swift` (new) pins, in the card's order:

* the bundled table is present and complete (`degradedReason == nil`, > 1,700 emoji, > 2,200 aliases);
* `dolphin`, `sparkling_heart`, `face_with_raised_eyebrow`, `camera_with_flash` draw their glyph,
  case-insensitively;
* **every** alias in the table resolves through `EmojiShortcodes.character(for:)` to the glyph the
  picker draws — one source, not a parallel list;
* the markdown renderer resolves the same names (`MarkdownText.accessibilityText`);
* a custom emoji image wins even when the name is also a system one; a not-yet-loaded image falls
  back to the system glyph; a name neither knows stays `:name:`.

`MattermostTests/T35ComposerViewModelTests.swift` gains `:dolph` → `dolphin`,
`:camera_with` → `camera_with_flash`, and `:thumb` → `thumbsup`.

One existing expectation had to change because it encoded the old sample: `T34EmojiTests
.testAnUnknownOrUnlistedShortcodeStaysText` used `:parrot:` as its "unlisted" example, and `parrot`
is a real system emoji (🦜). It now uses `not_a_real_emoji`; the custom-emoji case it also covers is
unchanged (`t34parrot` still resolves to the server image first).

## 6. What is *not* claimed

* `:lol-sob:` from the report is **not** in the upstream alias table (checked against the checked-in
  resource: no `lol-sob`, no `lol_sob`). It can only draw as an image if the server that posted it
  lists it as a **custom** emoji — which the pill already asks for first. On the local fixture
  server (9.11.19, `127.0.0.1:8065`, account `perfprobe`) the only custom emoji is `t34parrot`, so
  the `lol-sob` half of the report cannot be reproduced here; if that name is not a custom emoji on
  the reporting server, literal text is exactly what Mattermost's own web client draws too. This
  note does not pretend otherwise.
* A UI-level assertion of *which glyph* a pill drew is not possible through XCUITest: the pill is
  one combined accessibility element whose label is `"<name> <count>"`. The resolution order is
  therefore pinned as a unit test on `EmojiGlyph.resolve`, and the view body is a direct `switch`
  over its result rather than a second copy of the rule.
